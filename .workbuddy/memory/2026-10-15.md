# 2026-10-15

## GAS 溶解效果网络机制分析（UAbilityTask_Dissolve / GA_Enemy_Death_Base）

用户连续三轮追问"溶解效果为什么在客户端可见"，翻了 UE5.6 引擎源码（D:\UE_5.6\Engine\Plugins\Runtime\GameplayAbilities）+ 项目资产字符串 + Saved/Logs 旧日志，结论：

- ASC 复制条件（AbilitySystemComponent.cpp:1624-1658）：`ActivatableAbilities`（能力规格表）= COND_ReplayOrOwner，只发给 owner 客户端；`ReplicatedLooseTags` = COND_None 发给所有客户端；蒙太奇/Cue = 所有客户端。
- 敌人是 AI 拥有 → 敌人的 GA spec 不复制给任何客户端 → 敌人死亡 GA（含 DissolveTask）只在服务器跑。英雄的 spec 复制到自己的客户端，tag 触发器可在本地激活（MonitoredTagChanged → HasNetworkAuthorityToActivateTriggeredAbility）。
- 项目里死亡链路：WarriorAttributeSet(服务器) AddReplicatedLooseGameplayTag(Shared.Status.Dead) → GA_Enemy_Death_Base tag 触发 → 蒙太奇(PlayMontageAndWait, 复制) + ExecuteGameplayCue(GameplayCue.Enemy.Dissolve) + CreateDissolveTask。
- **【修正·用户实测为准】时间线是反的**：用户是先做 GameplayCue 版（GC_Enemy_Dissolve → StartDissolveOnActor），**Cue 版在客户端材质溶解没表现，只有 Niagara 粒子生效**；所以才改用 AbilityTask 版，Task 版客户端才看见。不要从资产字符串推因果——GA 资产里 GameplayCue.Enemy.Dissolve 与 CreateDissolveTask 字符串并存（节点删了字符串还在）。
- 10/12 日志证据（RPGDeemo-backup-2026.10.12-08.06.42.log）：StartDissolveOnActor 在 NetMode=2(Authority=1) 和 NetMode=3(Authority=0) 各执行一次 → Cue 路径确实在客户端执行了代码，Meshes=2(CharacterMesh0/EnemyHealthWidgetComponent)、Duration=3.00；但 PIE 在约 2 秒后被 tear down，客户端那份未跑完。粒子(NS_Dissolve_Glacer)在客户端有编译/播放记录。
- Cue 版客户端材质没表现的候选原因：(A) 定时器绑在 actor 弱引用上，客户端敌人被销毁/隐藏后定时器立刻清掉，参数停在近 0，而 Niagara 是世界空间独立 spawn 所以还在播；(B) 遍历式 SetScalarParameterValueOnMaterials 没打到可见材质槽（日志显示只有 1 槽，可能性较低）。未最终定论，需加日志验证。
- 仍成立的引擎事实：AbilityTask 与直接写在 GA 里的代码网络语义相同，都只在 GA 实例所在机器执行；敌人 spec(ActivatableAbilities=COND_ReplayOrOwner)不复制给任何客户端，故敌人 GA 正常只在服务器跑——若客户端能看到敌人溶解，需确认测的是否为本地控制的角色/是否看的是服务器窗口（曾用 C++ 日志 HasAuthority/NetMode 验证）。
- 其他遗留：GA_Enemy_Death_Base 资产里还残留旧版 Loop+Delay 节点；BP_EnemyCharacter_Base 实现了 BPI_EnemyDeath 接口（有 DissolveNiagaraSystem/DissolveTime 属性）；GA_Hero_Death 父类是 WarriorHeroGameplayAbility（C++），不含溶解。
- 敌人 ASC 的复制模式在 PossessedBy 里对玩家和 AI 统一设了 Mixed（AI 按最佳实践应为 Minimal，但不影响上述结论）。
